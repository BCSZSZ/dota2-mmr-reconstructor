0.5.4交互更新：候选名单及评分请求门槛降为至少2局，默认网页门槛仍为11局，可下调到2局。
每场内嵌日期、胜负、曲线分数、逐场分差、估算标识、详情完整状态及候选队友的死亡、K+A与评分；
空值保留null。曲线使用原 `curve_mmr_after`，不改变重建算法或将普通匹配画成0分。
图上框选、拖动边界或日期输入设置UTC日期区间，包含两端日期。按区间和普通匹配开关先筛比赛，
再汇总队友统计；各指标的有效样本数也必须达到所选最低局数。范围切换不自动降低最低局数。
共同比赛概览按比赛去重，MMR只累计区间内天梯的逐场分差，继续排除校准跳变。
网页与GUI将评分展示为“平均综合表现”，算法仍使用STRATZ的IMP。四个好榜在左、四个坏榜在右，
手机依次显示全部好榜再显示坏榜。HTML用一份逐场数据完成离线筛选，取代两份固定范围的汇总数据。

0.5.3范围更新：采集设置增加“队友报告包含普通匹配”，默认关闭。开启表示天梯＋常规普通匹配。
天梯仍严格来自 `mmr-dataset.json.rows`；普通匹配来自本次账号的 `gc-collection.json` 全部已下载历史，
不受MMR模型的起始日期限制。筛选 `LobbyType=0`，且游戏模式为AP、CM、RD、SD、AR、LP、CD或All Draft
（1、2、3、4、5、12、16、22），要求比赛ID、时间、胜负及模式字段明确存在，并按比赛ID去重。
排除Turbo、技能征召、活动、自定义和人机；模式编码依据 [Dota客户端协议枚举](https://github.com/SteamTracking/GameTracking-Dota2/blob/master/Protobufs/dota_shared_enums.proto)。
GC详情和STRATZ目标使用同一选定范围，沿用原缓存及同一次登录；请求清单分列天梯和普通比赛ID。
HTML同时内嵌仅天梯与合并范围的汇总，通过开关离线切换；各范围分别确定队友名单与局数门槛。
胜率、KDA、IMP按选定范围合并；MMR分差在普通匹配中为null，绝不增加真实或估算MMR样本。
上分／下分榜仍需至少11场共同天梯，概览分别展示天梯、普通局数并按比赛去重。
命令行 `--include-normal-matches` 与GUI开关一致，离线重建时仍不请求网络。

0.5.2交互更新：队友HTML改为八张Top 10横向柱状图，末位并列保留。最低同队局数可用滑块
或数字输入调整，从11局到本次数据中最高共同局数；不足10名时显示全部符合条件者。
筛选只改变入选名单，各队友统计仍使用其全部共同比赛。IMP、KDA各自11局有效样本的门槛不变。
概览的队友人数、去重共同比赛、共同净MMR及IMP覆盖率和完整名单一起更新。
HTML内嵌统计与每场队友归属，离线即可筛选，不触发GC或STRATZ请求。

默认范围沿用 `mmr-dataset.json.rows`，只分析MMR图表实际包含的天梯比赛。用户提供的

## 采集流程

一个EXE、一次Steam登录。先同步原GC历史与当前MMR并重建图表，再保持同一GC连接，
通过 `CMsgGCMatchDetailsRequest` 逐场补充缺失详情。保存10名玩家的账号ID、阵营槽位、
英雄、昵称及KDA，并保留protobuf字段缺失与显式0的区别。基础数据只来自GC。

详情串行请求，间隔1秒，单次超时20秒，超时重试一次；连续3场无响应则保存部分结果。
每场独立落盘，已有完整资料直接跳过；不完整资料下次重试。匿名对手不会妨碍队友统计。
`teammate-requests.json`列出范围内ID、GC待补ID、STRATZ目标及待补ID。

## 名单与算法

1. 按账号ID累计范围内不同比赛的同阵营出现次数。排除本人、对手、匿名ID。
2. 达到2场的账号进入候选名单，保留全部共同比赛样本；页面按所选日期和最低局数二次筛选。
3. 改名仍属于同一个ID；同名不同ID分开。此处的队友也包含反复匹配到的同阵营路人。
4. 根据入选名单生成STRATZ比赛集合，同局多人只请求一次。

胜率＝共同获胜场数/共同场数。场均死亡及场均K+A分别只用字段齐全的比赛。
平均IMP＝非空IMP总和/非空IMP场数；0为有效评分，胜负局等权。
正/负IMP分别取平均值最高/最低者。IMP来自STRATZ，不自行拼凑段位或英雄基准评分。
0是中性参照，不能将IMP描述成所有英雄都严格以0为均值的公开标准化公式。

逐场MMR取现有 `modeled_rank_change`：累计加分是正值之和，累计扣分是负值绝对值之和，
净变化是两者之差。净上分榜仅在正值中取最大，净下分榜仅在负值中取最小。
不计 `anchor_jump_before`，不对共同比赛首尾曲线作差，不再次乘双倍积分。
每位同局队友分别记完整分差，全体概览按比赛去重。实际与估算贡献分列展示。

各榜有效样本数需达到用户所选最低局数（默认11、最低2），Top 10末位并列保留，无符合条件者留空。
只表示同队时的结果与表现，不归因为某个队友独自造成输赢或分数变化。

## STRATZ与登录

使用官方GraphQL `https://api.stratz.com/graphql`：

```graphql
query($id: Long!) {
  match(id: $id) { id players { steamAccountId imp } }
}
```

请求使用个人Bearer令牌和 `STRATZ_API` User-Agent。仅请求选定范围中含入选队友的比赛，
每场间隔1秒，复用已有IMP；检查HTTP状态、GraphQL错误和返回比赛ID。限流时结束本次补分，
下次继续；空评分以后可重试，不填0。

首先读取按账号区分的Windows DPAPI加密令牌；无有效令牌时，用当前Steam会话刷新网页访问
凭据，尝试STRATZ的Steam OpenID跳转并读取其个人登录令牌。Steam网页cookie仅发往
steamcommunity.com；登录跳转限制在Steam和STRATZ的HTTPS域名。
该网站流程尚未在用户真实会话验证，不能承诺自动授权必定成功。
失败时GUI提供遮挡的令牌输入框、API页面链接和跳过按钮；不依赖网站匿名开发令牌。

## 输出与验证

原MMR报告先保存；队友报告输出独立HTML/JSON和请求清单。详情未齐、评分不足、中断或接口
失败均明确显示。`--reconstruct-existing --teammates`只读已有缓存，不登录、不请求网络。

自动验证覆盖11场门槛及回填、改名/同名、敌我阵营、匿名与缺字段、IMP空值/0、缓存续用、
共同MMR去重与锚点排除、HTTP/GraphQL错误、模拟OpenID跳转与HTML昵称转义。
保留原重建回归与凭据检查，并用用户的1,554场文件执行离线回放。
GC现场响应和STRATZ真实授权留待本次EXE试运行验证；缺基础缓存时，离线的0人结果只代表
资料未采集，不代表真实队友人数为0。
